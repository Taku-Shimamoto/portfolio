ゲーム内容

ゲーム説明

あなたは小さな町工場ではたらく社員。工場には古い機械が一つだけあり、常にだれかが稼働させないと故障してしまう。

製品の納期が10日後に迫る中、工場長から「働き方改革により、有給休暇を取得せよ」との通達が。

社員たちは、機械の稼働を止めることなく、有給休暇を取得しながら納期に間に合わせなければならない―――。

協力と駆け引きが織り成すゲームを制し、最も多くの有給休暇を取得できるのは誰だ...！？

主目的

  • チームで協力し、機械が故障しないように10ターンを経過させること(チームとしての目的)。
  • 他のプレイヤーの様子をうかがいながら、1回でも多く「非協力」に投票をすること(個人としての目的)。

遊び方

推奨人数

1チーム3～5人まで対応

所要時間

1ゲーム約20～30分

必要なもの

  • 本ゲームアプリ
  • 記録用紙

    (なくても楽しめますが、各ターンごとの投票内容や機械の稼働ステータスの変動値などを記録すると、ゲーム終了後に感想戦を楽しむことができます)

手順

  1. 1チームの人数を決め、対応するラジオボタン(3～5人)を選択します。
  2. 1人ずつ「協力」または「非協力」に投票します。順番は関係ないため、順番を決めても途中で変更してもかまいません。

    投票をやり直す場合は「やり直す」ボタンを押すと、最後に行った投票を取り消すことができます。

  3. 全員の投票が確定したら、「開票する」ボタンを押します。
  4. 「協力」「非協力」に投票した人数によって、機械の稼働ステータスが変動します。

    (ステータスの変動値は人数によって変わります。変動表は右上の「ステータス変動表を見る」をクリックするといつでも見ることができます)

  5. 記録用紙に自分の投票やステータス変動値などを記録します。記録用紙はゲームが終了するまでは他人に見せないでください。
  6. 1～5を10ターン繰り返します。
機械が途中で故障してしまったら？

機械が途中で故障してしまった場合、そのターンの最初から投票をやり直します。故障回数によって、プレイヤー全員が減点を受けます。

減点は機械が故障するたびに 1回: -1点、2回: -4点、3回: -9点 ... というように大きくなります。

ゲームの終了

10ターン経過でゲームが終了します。 「非協力」に投票した回数 - 減点数 が最終スコアとなります。

記録用紙をもとに感想戦を行っていただくと、より楽しむことができます。「このとき、どう考えた？」「このとき、どっちに投票した？」などたずねてみましょう。

複数回ゲームを行いその合計点で競う、ゲーム毎にチームを編成しなおす、などの楽しみ方もできます。

作者コメント

ゲームを振り返って

このゲームは「協力」と「駆け引き」の両方を同時に求められるというところが、とても新感覚で面白いゲームです。なぜならば、「機械を故障させない」というチーム共通の目的がありながらも、「1回でも多く非協力に投票する」という個人の目的があるからです。

「非協力」に投票して機械の稼働ステータスがマイナスになると、ステータスを戻すために協力を呼びかけ、誰かが「協力」に投票しなければなりません。そのタイミングで実際に「協力」を押すのか、それともだれかが「協力」を押していることを信じて「非協力」を押すのか、という駆け引きがとても楽しいゲームです。

ちなみに私は欲をかきすぎてしまい、機械を2回も故障させ、負けてしまいました...。その一方で、機械を一度も故障させることなく、「非協力」に8回も投票できたプレイヤーもいました。このゲームで勝つことができるのは、協力すべき場面でしっかりとチームに呼びかけ、「協力」に投票できる人なのかもしれません。

制作を振り返って

人数ごとにステータス変動値が変わる処理を、最初はif文を用いて書いていました。そうすると条件分岐があまりに多くなりすぎてかなり複雑なロジックになります。とても「他人や未来の自分が安心して触れる」ものではありません。

そのときちょうど出会ったのが「if文を用いた条件分岐」という視点から「オブジェクトで対応表をつくり、対応する値を取り出す」という視点への切り替えでした。

Before
const cooperative = votes.reduce((a, c) => a + c, 0,);
const uncooperative = players - cooperative;

if (cooperative === 0 && uncooperative === 4) {
    statusIndex -= 3;
} else if (cooperative === 1 && uncooperative === 3) {
    ...
} ...
After
const STATUS_TABLE = {
    3: [-3, -1, 0, 2],
    4: [-3, -1, 0, 1, 2],
    5: [-3, -2, -1, 0, 1, 2],
};

function calculateCooperativePlayers() {
    return votes.reduce((a, c) => a + c, 0,);
}

const cooperative = calculateCooperativePlayers();
statusIndex += STATUS_TABLE[players][cooperative];

見て分かる通り、if文の連鎖を書く必要が全くないので、コードの量が減りすっきりします。

加えて、 配列のインデックス番号 = 「協力」に投票した人の数 となるため、今後「一度に遊べる人数を6人に増やしたい」「ステータスの変動値を変えたい」などの仕様変更が起きてもSTATUS_TABLEを触れば良いということが一瞬で分かり、これは可読性と拡張性の面で効きます。

この考え方は後に作ることになる「アキネーターオセロ」での色の管理や「ドラフトしりとリレー」での状態管理においても大いに役立つものであり、その基礎をここで身に付けることができた、という意味ではとても大きな学びとなった制作体験でした。
